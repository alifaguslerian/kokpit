# Kokpit — Data Model

**Version:** 0.1  
**Status:** V1 Data Model Draft  
**Product:** Kokpit  
**Database:** Cloudflare D1  
**Object Storage:** Cloudflare R2  
**Scope:** Private single-user V1, multi-user-ready ownership  
**Last Updated:** 2026-10-06

---

# 1. Purpose

This document defines the persistent data model for Kokpit V1.

It describes:

- entities stored in Cloudflare D1
- files stored in Cloudflare R2
- relationships between entities
- ownership boundaries
- important constraints
- deletion behavior
- ordering behavior
- indexes
- timestamp conventions
- data that should not be persisted

This document defines **what Kokpit stores and how the stored data relates**.

Technical runtime decisions belong in `ARCHITECTURE.md`.

Actual migration files and ORM schema are implementation artifacts.

---

# 2. Data Model Principles

Kokpit V1 follows these principles:

1. **D1 stores structured metadata.**
2. **R2 stores file bytes.**
3. **User-owned entities carry `user_id`.**
4. **V1 has one owner, but the schema must not permanently assume one user.**
5. **IDs must be opaque and non-sequential.**
6. **Important ordering must be explicit.**
7. **External content must be normalized before storage.**
8. **Deleting a file-backed record must also clean up its R2 object.**
9. **AI-generated content must be distinguishable from sourced content.**
10. **The schema should remain simple enough to understand quickly.**

---

# 3. Storage Boundary

## Cloudflare D1

D1 stores:

- users
- settings
- ideas
- idea tags
- quick links
- semesters
- courses
- weeks
- material metadata
- track metadata
- playlists
- playlist membership
- news sources
- news articles
- quote pool
- small application state

## Cloudflare R2

R2 stores:

- audio files
- album artwork
- PDFs
- PowerPoint files
- Word documents
- images
- other uploaded academic files

D1 should never store large file bytes.

R2 should never be treated as the authoritative metadata database.

---

# 4. Identifier Strategy

Primary keys should use opaque string IDs.

Preferred:

```txt
UUID
```

Example:

```txt
8ef71f84-70d8-4a4f-b7f6-3f13296a6fcb
```

IDs should be generated by the application.

Do not expose sequential database row IDs.

All primary keys use:

```txt
TEXT PRIMARY KEY
```

unless implementation constraints justify another type.

---

# 5. Timestamp Convention

Persist timestamps in UTC.

Recommended representation:

```txt
ISO 8601 UTC string
```

Example:

```txt
2026-10-06T05:14:22.000Z
```

Common timestamp fields:

```txt
created_at
updated_at
deleted_at
published_at
last_shown_at
last_opened_at
```

The user's display timezone belongs in settings.

---

# 6. Ownership Model

Kokpit V1 has one seeded owner.

However, user-owned data should still include:

```txt
user_id
```

Ownership must exist on important top-level resources.

Examples:

```txt
ideas.user_id
quick_links.user_id
semesters.user_id
courses.user_id
materials.user_id
tracks.user_id
playlists.user_id
```

Even if ownership can technically be inferred through a parent relation, keeping `user_id` on security-sensitive resources makes authorization checks explicit and future multi-user migration safer.

# 7. Entity Relationship Overview

```txt
User
├── UserSettings
├── Ideas
│   └── IdeaTags
├── QuickLinks
├── Semesters
│   └── Courses
│       └── Weeks
│           └── Materials
├── Tracks
│   └── PlaylistTracks
│       └── Playlists
└── Playlists

NewsSource
└── NewsArticles

Quotes
```

Expanded College hierarchy:

```txt
User
└── Semester
    └── Course
        └── Week
            └── Material
```

Expanded Music relationship:

```txt
User
├── Track
└── Playlist
    └── PlaylistTrack
        └── Track
```

A track may appear in multiple playlists.

A playlist may contain many tracks.

# 9. Table: `user_settings`

Purpose:

Stores personal Kokpit preferences.

Relationship:

```txt
User 1 ─── 1 UserSettings
```

## Fields

| Field | Type | Required | Description |
|---|---|---:|---|
| `user_id` | TEXT | yes | Primary key + FK to users |
| `timezone` | TEXT | yes | Example: `Asia/Jakarta` |
| `locale` | TEXT | yes | Example: `id-ID` |
| `clock_format` | TEXT | yes | `12h` or `24h` |
| `quote_rotation_minutes` | INTEGER | yes | Fixed V1 value: `60`; local clock-hour rotation, not a configurable preference |
| `news_refresh_preference_minutes` | INTEGER | no | UI preference, not necessarily cron schedule |
| `music_volume` | REAL | yes | `0.0` to `1.0` |
| `sidebar_collapsed` | INTEGER | yes | SQLite boolean, `0` or `1` |
| `created_at` | TEXT | yes | UTC |
| `updated_at` | TEXT | yes | UTC |

## Constraints

```txt
PRIMARY KEY (user_id)
FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
```

## Defaults

Suggested:

```txt
timezone = Asia/Jakarta
locale = id-ID
clock_format = 24h
quote_rotation_minutes = 60
music_volume = 0.70
sidebar_collapsed = 0
```

For V1, `quote_rotation_minutes` must remain `60`. The primary quote changes at each local clock-hour boundary using `timezone`, not sixty elapsed minutes after opening Kokpit. V1 does not expose an interval setting.

# 18. College Deletion Behavior

Deleting:

```txt
Semester
```

should cascade:

```txt
Courses
→ Weeks
→ Material metadata
```

However, R2 objects are not automatically deleted by SQL foreign-key cascades.

The application must delete associated R2 objects as part of the deletion workflow.

Recommended service behavior:

```txt
collect affected material R2 keys
→ delete R2 objects
→ delete database hierarchy
```

If partial failure occurs, cleanup should be retried safely.

# 22. Music Deletion Behavior

Deleting a track should:

```txt
delete audio object from R2
delete optional cover object from R2 when uniquely owned
delete track row
```

`playlist_tracks` rows should cascade automatically.

Deleting a playlist should not delete tracks.

Deleting a playlist only removes:

```txt
playlist
playlist membership rows
playlist-specific cover if applicable
```

---

# 23. Playback State

The active playback session should primarily live in browser state.

Do not continuously write current playback position to D1.

Optional persisted state may include:

```txt
last_played_at
play_count
```

Future session-resume functionality may add dedicated state later.

V1 does not require it.

# 26. News Deduplication

`dedup_key` should be produced during ingestion.

Possible inputs:

```txt
normalized canonical URL
or
normalized title + source
```

Do not rely solely on database row IDs for duplicate detection.

Multiple articles about the same event are not automatically identical.

Event clustering is a future feature.

---

# 27. News Retention

Kokpit does not need to store news forever.

Suggested V1 retention:

```txt
30–60 days
```

Older articles may be deleted during scheduled maintenance.

Exact retention should remain configurable.

# 32. Data Not Stored in D1

Do not persist every transient UI event.

Examples:

```txt
current clock value
music progress every second
hover states
open dropdown
temporary modal state
loading state
temporary form text before save
current route
```

These belong in client memory.

# 33. Search

## Ideas

V1 idea search may use:

```txt
title LIKE
content LIKE
```

or SQLite FTS if useful during implementation.

Do not add external search infrastructure.

## College

Basic search may target:

```txt
course name
material title
filename
```

Global universal search is outside V1.

---

# 34. Ordering Strategy

Never rely on creation order where user-controlled ordering matters.

Use explicit `position` fields for:

```txt
quick links
semesters
courses
materials
playlists
playlist tracks
```

Recommended integer spacing when inserting:

```txt
100
200
300
400
```

or another implementation strategy that avoids unnecessary rewrites.

The exact reorder algorithm is an implementation detail.

---

# 35. Boolean Representation

D1 / SQLite booleans should use:

```txt
INTEGER
```

Values:

```txt
0 = false
1 = true
```

The application / ORM may expose them as real booleans.

---

# 36. JSON Usage

JSON should be used selectively.

Good use:

```txt
tiny flexible state
provider-specific metadata that is not queried
```

Avoid using JSON to replace relational structure.

Bad examples:

```txt
all playlist tracks in one JSON column
all courses in one semester JSON blob
all idea tags inside one comma-separated field
```

Important relational data belongs in normal tables.

---

# 37. Foreign Key Policy

Foreign keys should be enabled and defined where relationships are real.

Use:

```txt
ON DELETE CASCADE
```

when child records have no meaning without their parent.

Examples:

```txt
semester → course
course → week
week → material
playlist → playlist_tracks
idea → idea_tag_links
```

Do not cascade from playlist to track.

---

# 38. Ownership Query Rule

Application queries for user-owned resources must include `user_id`.

Bad:

```sql
SELECT *
FROM ideas
WHERE id = ?;
```

Preferred:

```sql
SELECT *
FROM ideas
WHERE id = ?
AND user_id = ?;
```

The same rule applies to:

```txt
materials
tracks
playlists
quick links
semesters
courses
weeks
```

even in single-user V1.

---

# 39. R2 Key Rules

R2 keys should be generated by the backend.

Conceptual layout:

```txt
users/{userId}/music/audio/{trackId}/{filename}

users/{userId}/music/covers/{trackId}/{filename}

users/{userId}/college/{courseId}/{weekId}/{materialId}/{filename}

users/{userId}/playlist-covers/{playlistId}/{filename}
```

Do not derive authorization purely from the key.

Authorization comes from D1 ownership checks.

---

# 40. File Name Policy

Store both:

```txt
original_filename
r2_key
```

The original filename is for display.

The R2 key is controlled by Kokpit.

Do not directly use untrusted original filenames as complete storage paths.

Sanitize filenames when required.

---

# 41. File Size Policy

Suggested V1 application upload limit:

```txt
50 MB per file
```

Persist actual size in:

```txt
size_bytes
audio_size_bytes
```

This limit may change later without redesigning the data model.

---

# 42. Soft Delete Policy

Kokpit V1 does not require broad soft deletion.

Default behavior:

```txt
real delete
```

for:

- ideas
- links
- playlists
- courses
- materials
- tracks

If trash / restore becomes a product requirement later, add:

```txt
deleted_at
```

where appropriate.

Do not introduce soft-delete complexity before it is needed.

---

# 43. Audit History

Full revision history is outside V1.

Kokpit does not need:

```txt
idea revision tables
material audit logs
playlist history
user activity ledger
```

Git tracks code changes.

The application database only tracks current user content plus lightweight timestamps.

---

# 44. Derived Data

Prefer deriving simple values instead of storing duplicates.

Examples:

```txt
playlist track count
course material count
semester course count
```

can usually be queried.

Store derived values only if real performance requirements appear.

---

# 45. Data Model for Home

Home should not have a dedicated `home_widgets` table in V1.

Home reads summaries from existing entities.

Examples:

```txt
current music
→ client playback state + tracks

college highlight
→ active semester + latest relevant course/week

news highlight
→ news_articles

idea capture
→ ideas

quick links
→ favorite quick_links

quote
→ quotes
```

Home is a composition layer, not a separate data domain.

---

# 46. Recommended Initial Seed Data

Initial production setup may seed:

```txt
1 owner user
1 user_settings row
news_sources
small emergency quote fallback pool
```

Do not seed fake college data, fake ideas, or fake music into production.

Development fixtures may use sample data separately.

# 50. Data Model Rules for AI Agents

AI coding agents working on Kokpit must:

1. Treat this document as the data-model source of truth.

2. Do not create new persistent entities without a real product requirement.

3. Keep file bytes in R2, not D1.

4. Keep file metadata in D1.

5. Preserve `user_id` ownership.

6. Use foreign keys for real relationships.

7. Use migrations for every schema change.

8. Keep user-controlled ordering explicit with `position`.

9. Do not use JSON blobs to avoid proper relational modeling.

10. Do not fabricate quote authors.

11. Keep AI enrichment optional.

12. Preserve original article URLs and source information.

13. Do not create a dedicated Home data table unless product requirements change.

14. Update this document if the persisted schema changes materially.

15. Keep the model simple enough that another developer or coding agent can understand it quickly.

---

# 51. Final Data Model Lock

Kokpit V1 data is divided into six main domains:

```txt
Identity
→ User
→ Settings

Personal Capture
→ Ideas
→ Idea Tags

Library
→ Quick Links

College
→ Semester
→ Course
→ Week
→ Material

Music
→ Track
→ Playlist
→ Playlist Track

External Content
→ News Source
→ News Article
→ Quote
```

The core storage rule is:

> D1 knows what something is. R2 stores the bytes when that something is a file.

The core ownership rule is:

> Every personal resource belongs to a user, even while Kokpit V1 has only one user.

The core complexity rule is:

> Add structure only when the product actually needs it.
